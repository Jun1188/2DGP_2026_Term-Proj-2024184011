# 윷토체스 프로젝트·프로토타입 제작 루틴

**2026-11-09 기준 제작 계획** · 과제 시연의 첫 목표는 **Python 이식의 첫 1막 3라운드 PvE**다. HTML 박싱은 현재 3막 9라운드이며, 아래 일정은 Python 제작 계획과 구분한다. 플레이어는 한 라운드에서 완주한 말의 weight 합계로 목표 점수 이상을 달성해야 한다. 초과 점수와 보너스는 유지하고, 수문장은 지정 길목에서 전투한다. 첫 콘솔 판에서 이 규칙을 확인하고, 같은 판을 pico2d에서 다시 플레이한 뒤, 상점에서 고른 윷이 다음 라운드의 선택을 어떻게 바꾸는지 확인한다. 규칙의 기준은 [수정 기획서](yutochess-revised-design.md), 밸런스 초깃값과 윷판 경로의 출처는 [게임 데이터](detailed-design/game-data.json)다.

## 한 번의 제작 반복

1. **판단 하나를 고른다.** 예를 들어 미완주 말의 weight는 높지만 정산 점수는 목표 미달인 상황에서 ‘수문장 앞에서 업을까, 지금 완주할까’를 검증한다. 시작 상태, 시드, 선택한 윷과 말을 보관한다. 두 선택은 같은 투척 직후 상태에서 갈라져야 한다.
2. **화면 껍데기와 HUD를 먼저 잇는다.** 도형으로 손패·말·버튼을 배치해 한 턴을 끝까지 누를 수 있게 한다. 정산 점수/목표, 말별 weight, 남은 투척, 수문장·추가 보스의 주둔 칸·도착 전투 예측·마스터 갱신 예고을 표시한다. 말을 누르면 도착 칸과 예상 사건이 바뀐다.
3. **실제 판정으로 교체한다.** 화면 입력을 규칙 코어에 보내 이동·업기·전투·완주와 weight 누적·정산 내역을 받는다. 같은 선택의 미리보기와 확정 결과를 대조하고, 정산 직후 상태에서 다음 손패나 결과 화면까지 진행한다.
4. **두 선택을 직접 비교한다.** 플레이어에게 선택 이유와 예상 도착점을 물은 뒤 실제 이동·점수 로그와 맞춰 본다. 예고를 놓쳤으면 HUD를, 예고와 실제 결과가 다르면 판정이나 표시를 고친다. 무엇을 바꿨는지 한 줄로 남기고 같은 장면을 다시 본다.
5. **레퍼런스로 에셋을 만들고 적용한다.** 기본 제공 리소스 대신 레퍼런스 이미지를 컨텍스트로 넣어 GPT Image로 만든다. [투척 화면 콘셉트](detailed-design/img/toss-screen-concept.png)에서 팔레트·카메라 시점·외곽선 굵기·광원 방향을 정해 공통 프롬프트에 기록한다. 첫 묶음은 윷 앞뒤·표시 윷·내 말·수문장이다. 게임 크기로 올려 앞뒤, 표시, 겹친 말 수, 적의 예고가 한눈에 구분되는지 본다. 채택본에는 원본 레퍼런스, 프롬프트, 적용 장면을 연결해 다음 묶음에도 같은 기준을 쓴다. 프롬프트 형식은 아래 [이미지 프롬프트 틀](#이미지-프롬프트-틀)을 쓴다.

### 이미지 프롬프트 틀

[OpenAI 이미지 프롬프트 가이드](https://developers.openai.com/api/docs/guides/image-prompting)의 권고를 아래 네 칸으로 나눠 적는다. 칸을 섞지 않아야 수정 요청에서 무엇이 바뀌었는지 추적된다.

| 칸 | 적는 내용 | 윷가락 예시 |
|---|---|---|
| 주제·용도 | 무엇을, 어디에 쓰는가 | 게임 손패 카드에 쓰는 윷가락 1개, 배(평평한 면) |
| 구도·스타일 | 시점, 배치, 화풍, 팔레트, 외곽선, 광원 | 정면, 중앙 배치, 투명 배경, 콘셉트 이미지와 같은 팔레트·외곽선 굵기, 좌상단 광원 |
| 반드시 지킬 조건 | 크기, 배경, 금지 요소, 다른 에셋과 맞출 특징 | 256×256, 그림자 없음, 글자 없음, 기존 '등' 이미지와 같은 길이·나뭇결 |
| 글자 (있을 때만) | 정확한 문구를 따옴표로, 위치·글꼴·등장 횟수 | 표시 윷 배면 중앙에 "X" 1회, 붓글씨 |

기존 이미지를 고칠 때는 **바꿀 대상과 유지할 요소**를 모두 적는다(예: "표시 X의 굵기만 1.5배, 나뭇결·색·크기·외곽선은 유지"). 복잡도(구도와 배치를 얼마나 계획할지)와 화질(질감·작은 글씨의 세밀함)은 별개 설정이다. 단일 아이콘은 복잡도를 낮추고, 글자가 들어간 UI 장식은 화질을 올린다. 채택한 프롬프트는 JSON으로 남긴다(`schemaVersion`, 에셋 `id`, 레퍼런스 경로, 네 칸 내용, 복잡도·화질, 채택 파일, 적용 장면).

## 규칙 코어와 제작용 진입점

| 경계 | 입력과 결과 |
|---|---|
| 규칙 코어 | 게임 데이터 버전과 시드로 난수를 초기화한다. 런 상태에는 덱·강화·부적·엽전을, 라운드 상태에는 손패·말의 경로 이력·주둔 수문장·추가 보스·마스터 계획·특수칸·투척·정산 점수·말별 weight/HP/공격/속도/계수·정산 완료 여부를 둔다. 합법 입력 한 건으로 다음 상태와 순서 있는 사건·점수 내역을 만든다. |
| 콘솔·pico2d·향후 봇 | 모두 같은 규칙 코어에 입력한다. pico2d는 결과를 받아 그리거나 재생한다. 미리보기와 애니메이션에 게임 난수를 소비하지 않아야 같은 시드와 입력이 같은 판을 만든다. |
| 종료와 데이터 | 게임 데이터 1.6.0-draft의 `rules.scoring`과 `rules.endRoundOnTarget`을 읽어 완주 weight만 라운드 점수에 가산하고 목표 이상인지 판정한다. 별도 완주 개수 조건은 없다. 초과 점수·보너스는 보존한다. 종료된 라운드는 보상 지급 후 다시 정산할 수 없게 한다. [결정 3](detailed-design/index.html#decisions) |

### 아키텍처 선택

폴더 구조와 핵심 객체(`RunState`·`RoundState`·`Piece`·`ScoreContext`·`Effect` 훅)는 [상세 기획서 14장](detailed-design/index.html#impl)을 그대로 따른다. 메모에 적은 후보 아키텍처는 아래처럼 적용 범위를 정한다.

| 후보 | 적용 여부 | 이유와 위치 |
|---|---|---|
| OOP 상태 객체 + 사건 로그 | 채택 | 판 위 개체가 말 4개와 수문장 2개·추가 보스 0~3개뿐이고, 규칙이 '합법 입력 1건 → 다음 상태 + 사건 목록'으로 정리된다. 사건 로그가 리플레이·연출·Hub 대조의 공통 형식이 된다. `core/` |
| 장면 스택 | 채택 | 수업 프레임워크의 `change_mode`/`push_mode`/`pop_mode`를 쓴다. 장면은 규칙 코어를 호출하고 사건을 재생만 한다. `modes/` |
| ECS | 보류 | 개체 수가 적어 컴포넌트 분리 이득보다 조회 비용이 크다. 숫자 팝업·파티클 같은 연출 개체가 수백 개로 늘 때 `ui/fx.py` 안에서만 다시 검토한다. |
| 그래프 최단 경로 (BFS/A*) | 1막 이후 | 전통 29칸과 완주 관문의 그래프라 BFS로 충분하다. 봇의 '몇 투척 뒤 어느 길목에 닿는가' 평가에 쓴다. PvE 수문장·보스는 고정 위치를 유지한다. 칸 위험도에 가중치를 붙일 때 A*로 바꾼다. `core/board.py` |
| C++ 모듈 · 서버 래핑 | 측정 후 | 코어의 공개 함수를 `step(state, action) → (state, events)` 하나로 유지한다. 그러면 병목 함수만 C++로 바꾸거나, PvP 호스트 프로세스가 같은 함수를 감싸 서버로 돌릴 수 있다. 파이썬판과 같은 입력의 사건 로그가 일치해야 교체를 인정한다. |

제작용 진입점은 아래 세 가지다. 콘솔 코어와 장면이 생기는 순서에 맞춰 연결한다.

| 진입점 | 필요한 입력 | 기대 결과 |
|---|---|---|
| 개별 장면 열기 | 장면 이름과 시작 상태 | 손패 선택, 수문장 직전, 정산, 상점 등을 전체 런 진행 없이 열고 실제 다음 장면으로 전환한다. |
| 고정 시드 재생 | 데이터 버전·시드·초기 상태·순서 있는 입력열 | 사건별 이동·점수·추가 투척·승패 요약을 남긴다. 장면 중간에서 시작하면 해당 시점의 난수 상태까지 복원한다. |
| 밸런스 집계 | 시드 집합·덱·구매/강화·말 선택 방침·데이터 버전 | 라운드별 시도와 성공 수, 실패 사유, 완주 수, 남은 투척을 집계한다. 실제 플레이 시간은 사람이 조작한 런에서 별도로 잰다. |

## 장면 분리와 검증

11/9 확인한 로컬 추적 참조 `origin/develop`은 상세 기획서 추가 전 커밋 `65251de`였다. 구현을 시작할 때 원격과 로컬의 기준점을 다시 비교하고 최신 기획 데이터가 들어간 개발 기준에서 `develop` 장면 작업을 시작한다. 로직의 기대값은 Python 표준 `unittest`에 둔다. Hub 디버거와 상호 확인할 때는 동일한 버전·시드·초기 상태·입력열·기대 로그를 사용해 **처음 달라진 턴과 사건**을 기록한다. Hub 연동의 완료 근거는 양쪽 실행에서 수집한 로그다.

| 재현할 상황 | 기대 결과 |
|---|---|
| 표시 윷만 배가 나온 빽도. 대각선 진입 후 빽도, 판 위 말이 없는 빽도 | 이동 이력의 직전 칸으로 돌아간다. 판 위 말이 없으면 weight와 라운드 점수 모두 증가하지 않는다. |
| 모서리·중앙을 지나기와 그 칸에서 다음 턴 시작하기 | 통과할 때는 현재 길을 따른다. 5·10·중앙에서 다시 출발하고 남은 길이 다르면 현재 길/지름길을 선택한다. [경로 예시](detailed-design/index.html#board) |
| 두 말을 업고 완주하거나 수문장에게 잡힘 | 낮은 weight 말의 지원이 높은 주말을 증폭한다. HP/공격은 별도 기본값·계수·윷 배율로 연동한다. HP/weight 0인 말은 사망해 미정산 weight를 잃고, 생존 완주 말만 한 번 정산한다. |
| 마지막 투척에서 완주 정산으로 목표 달성, 또는 목표 미달 | 정산 점수가 목표 이상이면 승리하고 초과 점수·보너스를 유지한다. 목표 미달이라도 추가 투척과 움직일 말이 있으면 계속한다. 미완주 weight는 판정에 쓰지 않는다. 투척 소진 또는 전원 완주 상태에서 목표 미달이면 패배한다. |
| 보상 버튼 재입력, 상점 구매·강화 후 라운드 전환, 결과에서 재시작 | 한 라운드의 보상은 한 번만 지급된다. 변경된 덱과 잔액은 다음 라운드에 유지되고 새 런에서는 시작 덱과 시작 재화로 돌아간다. |
| 고정된 윷 조합, 마스터 세 번째 턴 갱신 | 투척 확률은 상세 기획서 계산기와 비교한다. 수문장·일반 보스는 도착 칸에서만 교전하고, 게임 마스터는 예고한 특수칸 위치·개수·종류·판 전체 특성을 갱신한다. 턴말 weight 손실도 같은 예측/확정 계산을 사용한다. [투척 계산기](detailed-design/index.html#calc) |

밸런스의 첫 비교값은 **기본 덱 1-1 클리어율 90% 이상, 무강화 1-3 클리어율 30% 이하, 실제 라운드 평균 3~4분**이다. 클리어율은 해당 라운드 진입 수를 분모로 삼는다. 실패는 투척 소진·전투 패배·완주 정산액 부족을 사건 로그로 구분한다. 동일 시드 묶음과 행동 방침으로 변경 전후를 비교하고, 목표 점수 조정이 완주 횟수와 정산 weight에 미친 영향도 함께 본다. 제출 전 실제 플레이 10회는 진행·조작 확인 기록으로 쓰며, 클리어율 표에는 별도로 측정한 시도 수를 명시한다. [기존 검증 목표](detailed-design/index.html#test)

## 환경 준비와 1막 이후 작업

- **Python과 pico2d.** 11/9 기본 인터프리터는 Python 3.14.4이고 그 환경에서 `pico2d` 패키지는 발견되지 않았다. PyPI 최신판은 1.5.1이다. 콘솔과 규칙 테스트는 표준 라이브러리로 시작한다. 그래픽 단계에서는 프로젝트 가상환경에 설치할 후보를 정하고, 설치 후 창 열기 → 키·마우스 입력 → 정상 종료를 확인한다. 동작한 Python·pico2d 버전과 실행법을 기록한다. Python 3.14 호환 여부는 이 확인이 남아 있다. [pico2d 공식 배포 정보](https://pypi.org/project/pico2d/)
- **게임·에셋 스킬.** 11/9 확인 범위에서 `codixel`, `pixelfx`, `create-game-assets`의 현지 설치 완료 근거는 확보되지 않았다. 이미지 생성·시트 가공 단계에 들어갈 때 현지 스킬 카탈로그에서 역할과 경로를 확인하고, 하네스가 해당 스킬을 발견하는지 확인한다. 기존 도구로 충족되지 않는 작업만 설치 후보와 이유를 남긴다. 후보의 용도는 [첨부 메모](../to-do-job.md)에서 확인할 수 있다.
- **봇·적응형 호스트와 2인 대전.** 1막 완료 후 같은 판에서 규칙 기반 봇이 합법 행동을 선택하도록 한다. 행동 트리는 목표 부족분과 예고된 위협을 읽고, 경로 선택지가 있는 상황에서 최단 경로 평가의 실익을 비교한다. 같은 행동 트리를 호스트 쪽에도 써서 고정 주둔지·공격 범위 안의 다음 전투 행동을 고르되, [예고 규칙](yutochess-revised-design.md#호스트와-이후-모드)을 지키는지 같은 시드 재생으로 확인한다. PvP는 한 클라이언트가 방을 호스팅해 입력 검증·난수·턴 순서·결과 확정을 맡는다. 두 클라이언트가 같은 턴과 결과를 표시하는 한 판으로 검증한다. 상대 점수 경쟁의 종료 조건은 이 단계에서 봇 대전과 함께 구체화한다.
- **C++와 로컬 모델.** 규칙 계산·경로 탐색의 비용을 먼저 재고 병목인 연산만 C++ 호출 경계로 옮긴다. Python 기준판과 같은 입력의 결과·호출 비용을 비교한다. 로컬 디시전 모델과 LLM은 합법 행동 후보를 고르는 비동기 실험으로 둔다. 장면 연출 중 후보를 준비하고, 턴의 시간 예산 안에 유효한 응답이 없으면 규칙 기반 행동을 적용한다. 채택 근거는 기준 봇 대비 응답 지연, 시간 초과율, 합법 행동률, 같은 시드에서의 플레이 결과다. [OpenDecision 원본 저장소](https://github.com/deepanwadhwa/OpenDecision)

## HTML 박싱 선행 구현 (2026-11-09)

[기획서 박싱 영역](detailed-design/index.html#boxing)에 플로차트 기반 3막 9라운드 루프와 장면 편집기를 작성했다. 이후 Python 코어를 만들 때 실제 규칙을 대조할 선행 프로토타입이다. `boxing-core.js`·`boxing-game.js`·`design-view.js`·`boxing-game.css`는 JavaScript 박싱 구현이며 위 pico2d 제작 일정의 완료를 대신하지 않는다.

수동 확인은 [박싱 안내](detailed-design/README.md)의 순서로 사용자가 수행한다. 편집기로 시작 상태를 만들고 같은 시드·고정 결과·사건 기록을 저장할 수 있다. 이 작업에서 빌드·게임 실행·테스트는 수행하지 않았다.

## 현행 규칙과 초반 확인 순서

1. 선택형 첫 3턴 체험에서 낮은 말 업기 → N × M·weight 폭발 → 별도 HP·공격 성장을 먼저 확인한다. 실제 난수 런과 구분한다.
2. 바로 시작은 기본 덱·정석·8개 윷으로 출전한다. 다른 시작 설정의 리스크는 3개다. 첫 라운드는 보너스 칸 2개·고요한 판으로 제한한다. 이후 마스터의 작은 디메리트, 속도·공격 보상과 추가 보스 기믹을 소개한다.
3. 초기 리스크 픽, 구매 덱 카드, 마스터 판 전체 특성의 세 부류를 구분한다. 상대적인 효과 스케일과 초반 정보량을 사용자 플레이로 조정한다.
4. 지름길·관문 수문장 2체와 픽의 일반 보스 수·HP·공격·기믹, 특수칸 도착 효과·3턴 갱신·턴말 효과를 같은 상태에서 예측/확정한다.
5. 윷 반환·셔플, 매 라운드 출전 편집, 상점의 덱·말 성장과 장면 저장·복원을 확인한다.
6. 3초 이름 회상·약 30분 자발적 세션·종료 3시간 내 비유도 회상을 기록한다. 작성 완료를 재미·몰입의 검증으로 대체하지 않는다.

위 확인은 사용자가 수행한다. 이 작업에서 빌드·실행·테스트는 하지 않는다.

## 1.5 박싱 조작·보드 보정

첫 3턴 선택형 체험은 도→걸→모를 표시한다. 매턴 윷 드로우→손패 공개→직접 4개 선택을 거친 뒤 투척하고 자동 이동한다. 실제 갈림길만 선택하며 첫 시작 설정·상세 편집은 접는다. 큰 이동 칸수와 N × M × X 결과를 보드 위에서 확인한다.

전투는 HP 박스·막대·선공/반격 타격·피해 숫자로 표현하고 결과는 계속 버튼까지 유지한다. 외곽 정사각형과 대각선은 귀환 J에서 만나며, J 아래 G와 END를 수직 연결한다. 장면 데이터 1.5에서 이 경로와 진행 말·직전 결과를 저장한다. 빌드·실행·테스트는 사용자에게 맡긴다.


## 1.6 추가 수정 (2026-11-10)

수문장 옆 출발 0에서 코스를 돌아 귀환 J를 거친 뒤 G로 진입한다. 출발 대기 말도 표시하며, 미출발 말을 귀환 말이 업어 완주하지 않게 논리 위치를 구분한다. 투척 전 다음 첫 칸·결과별 도착 후보, 투척 후 경로·순번을 강조한다.

수문장 weight·공격과 라운드 성장 계수를 높였다. 지름길 단독 선공 ×0.6 / 업기 선공 ×1.25, G 받는 피해 ×0.75 / 절반 HP 반격 ×1.5다. 첫 라운드는 일반 보스 0체, 둘째부터 기본 일반 보스+리스크 픽 추가다. 실제 난도는 사용자 확인 전이다.

라운드 결과 → 다음으로(보상 1회) → 상점 / 추가 이자 선택으로 진행한다. 추가 이자는 상점을 건너뛰고 보상 후 잔액 기준 이자를 추가 1회 받는다. 마지막 라운드는 런 결과로 간다. 상점 상단은 현재 금액·다음 라운드 예상 이자만 표시한다. 윷 구매·덱 편집과 특성 구매를 분리하고 윷 강화는 덱 편집 토글 안 아래, 말 강화·특성은 각 말 카드에 둔다. 말·윷·특성의 고정 SVG 아이콘과 복합 효과 조합을 제공한다.

[박싱 안내](detailed-design/README.md)의 1.6 사용자 확인 항목을 따른다. 빌드·실행·테스트는 사용자에게 맡긴다.


## 손패 직접 선택과 수치 편집 (2026-11-10)

매턴 드로우→새 윷 공개→직접 4개 선택→투척→사용 윷 반환·셔플을 차례로 보여준다. 자동 선택과 접힌 손패 선택을 제거했다. 사용하지 않은 손패는 유지하고 다음 턴 부족한 수만 보충한다. 교체도 반환→드로우→공개→선택을 거친다.

편집기는 기본 weight·HP·공격과 추가 HP/공격 배율만 입력한다. 현재 HP·최대 HP·공격은 읽기 전용 결과이며 적용 예정 수치와 실제 적용을 같은 계산으로 처리한다. 받은 피해량을 보존하고, 추가 배율은 윷 자동 배율 갱신과 분리해 유지한다. 보스 위험도는 기본값·weight와 중복 적용하지 않고 HP/공격 자동 배율에 각 1회 반영한다. 빌드·테스트는 사용자에게 맡긴다.

덱·손패·던지기는 보드 아래 하단 조작 영역에 둔다. 드로우 시 덱에서 손패로 이동하는 모션 후 공개하며 사용할 윷은 손패 내 강조+12px 올림으로 표시한다. 별도 사용 슬롯은 없고 4개 선택 제한·재클릭 해제를 지원한다.
